# План за упражнение (Q&A формат): Generics and Traits II

## ⏱️ Час 1: Теоретичен преговор и ключови концепции

### 1. Generics и Trait Bounds

* **Въпрос 1.1:** *Какво печелим от използването на generic типове и trait bounds спрямо динамичния полиморфизъм (`dyn Trait`) по време на изпълнение?*
  * **Отговор:** При generic типовете компилаторът на Rust използва процес, наречен **monomorphization** (мономорфизация). Това означава, че за всеки конкретен тип, с който се извика функцията/структурата, компилаторът генерира отделно машинно копие. Това осигурява максимална бързина (zero-cost abstractions) и възможност за инлайнване (inlining), за разлика от `dyn Trait`, който използва таблици с виртуални функции (vtables) и динамично насочване (dynamic dispatch) при всяко извикване.
  * **Пример за дискусия:**
    ```rust
    // Какво се случва при компилация с този код?
    fn print_item<T: std::fmt::Display>(item: T) {
        println!("{}", item);
    }
    
    fn main() {
        print_item(42);       // Генерира се версия за i32
        print_item("hello");  // Генерира се версия за &str
    }
    ```

### 2. Сравнение и еквивалентност: `PartialEq` спрямо `Eq`

* **Въпрос 2.1:** *Защо в Rust има два отделни трейта за еквивалентност (`PartialEq` и `Eq`), вместо само един?*
  * **Отговор:** Защото не всички типове в математиката и компютърните науки могат да се сравняват напълно. `PartialEq` изисква само симетричност и транзитивност, но **не и рефлексивност**. Най-яркият пример са числата с плаваща запетая (`f32` и `f64`), при които специалната стойност `NaN` нарушава правилото, че всяко нещо е равно на себе си (`NaN == NaN` е `false`). Трейтът `Eq` е празен (маркерен) трейт, който казва на компилатора: *"За този тип гарантирам, че `a == a` е винаги `true`"*, което е задължително, ако искаме да ползваме типа като ключ в `HashMap`.
  * **Пример за дискусия и въпрос към студентите:**
    ```rust
    #[derive(PartialEq)]
    struct Point {
        x: f32,
        y: f32,
    }
    
    // Въпрос: Защо компилаторът НЕ позволява да сложим #[derive(Eq)] тук?
    // Отговор: Защото полетата x и y са f32, а f32 имплементира само PartialEq, не Eq.
    ```

### 3. Предоставени методи в трейтовете (Default Implementations)

* **Въпрос 3.1:** *Каква е ползата от дефинирането на тяло по подразбиране (default implementation) в методите на един трейт?*
  * **Отговор:** Това позволява на създателя на трейта да предостави обща функционалност, която имплементиращите структури получават наготово, без да се налага да я повтарят. Освен това позволява безопасна еволюция на интерфейсите (backward compatibility) – ако добавим нов метод с дефолтна реализация към съществуващ трейт, старите имплементации на студентите няма да се счупят при компилация.
  * **Пример за дискусия:**
    ```rust
    trait Greeter {
        fn name(&self) -> &str; // Задължителен метод
        
        // Предоставен метод по подразбиране
        fn greet(&self) {
            println!("Hello, {}!", self.name());
        }
    }
    ```

## ⏱️ Час 2: Практически задачи и код за упражнение

### Задача 1: Иплементиране на `PartialOrd` и сравнение

* **Въпрос към студентите:** *Как бихме могли да сортираме списък от наши собствени структури (напр. `Student`), ако вече сме имплементирали `PartialEq`?*
  * **Отговор:** Трябва да имплементираме трейта `PartialOrd`, който дефинира метода `partial_cmp`. Той връща `Option<Ordering>`, защото при плаващи запетая или custom логика сравнението може да е невъзможно (`None`).
  * **Примерен код за демонстрация в час:**
    ```
    use std::cmp::Ordering;

    #[derive(Debug)]
    struct Student {
        name: String,
        score: f64,
    }

    impl PartialEq for Student {
        fn eq(&self, other: &Self) -> bool {
            self.score == other.score
        }
    }

    impl PartialOrd for Student {
        fn partial_cmp(&self, other: &Self) -> Option<Ordering> {
            self.score.partial_cmp(&other.score)
        }
    }
    
    // Въпрос към студентите: Какъв метод ще могат да извикат върху колекция от Student след това?
    // Отговор: .sort_by(...) или просто .sort() ако имплементираме и Ord.
    ```

### Задача 2: Асоциирани типове в Трейтове (на базата на `Iterator`)

* **Въпрос 2.1:** *Защо в трейта `Iterator` типът на елементите (`Item`) е дефиниран като **асоцииран тип** (`type Item;`), а не като generic параметър на самия трейт (`trait Iterator<T>`)?*
  * **Отговор:** Ако `Iterator` беше generic трейт (`trait Iterator<T>`), една структура би могла да имплементира `Iterator<i32>` и `Iterator<String>` едновременно за едно и също нещо, което създава неясноти и усложнява типовата система. Чрез асоциирания тип `type Item`, всеки тип може да има **само една** валидна имплементация на `Iterator` в даден контекст, което прави кода много по-чист и предсказуем.
  * **Примерен код за дискусия (Прост брояч):**
    ```rust
    struct Counter {
        current: usize,
        max: usize,
    }

    impl Iterator for Counter {
        type Item = usize; // Дефиниране на асоциирания тип

        fn next(&mut self) -> Option<Self::Item> {
            if self.current < self.max {
                let val = self.current;
                self.current += 1;
                Some(val)
            } else {
                None
            }
        }
    }
    ```
